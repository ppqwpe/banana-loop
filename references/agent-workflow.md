# 환경별 진행과 에이전트 응답

스킬을 읽는 에이전트의 이름보다 실제 가능한 작업이 중요하다. 파일 접근, 코드 실행, 브라우저 연결은 서로 다른 능력이다. 하나가 가능하다고 나머지도 가능하다고 안내하지 않는다. 아래 틀은 필요한 정보만 짧게 전달하기 위한 기준이며, 사용자가 이미 제공한 정보를 다시 묻는 양식이 아니다.

## 자료를 받았을 때의 첫 안내

자료를 확인한 뒤 3~5문장으로 말한다. 다음 틀의 대괄호는 실제 확인한 내용으로 바꾼다.

> [캐릭터 이미지와 배경 이미지, 시놉시스]를 확인했어요.
> 요청하신 작업은 **[여러 레퍼를 순서대로 생성]**하는 방식으로 진행할게요.
> [이미지별로 요청에 맞는 프롬프트를 준비하고, 한 이미지의 묶음이 끝나면 다음 이미지로 교체합니다.]
> 먼저 [원본을 보존해 작업 순서를 정리하고 실행 파일을 만들겠습니다].

자료만 있고 목적을 알 수 없으면 마지막 문장을 “먼저 캐릭터 변형부터 해볼 수 있어요. 어떤 결과를 만들고 싶으세요?”처럼 바꾼다. 작업 목적이 이미 명확하면 묻지 않고 진행한다. 프롬프트 개수 등 실행 준비에 필요한 정보가 빠졌으면 그 항목만 묻는다. 미확인 자료가 있으면 읽은 범위와 누락 항목을 짧게 구분한다.

세 방식별 설명은 한 문장이면 충분하다.

- **텍스트로 생성:** “시놉시스에 맞는 프롬프트를 준비하고, 이미지 첨부 없이 순서대로 실행할게요.”
- **레퍼 한 장으로 생성:** “같은 원본을 유지하면서 요청하신 의상·헤어 등의 변형을 차례로 만들게요.”
- **여러 레퍼를 순서대로 생성:** “01번 원본의 프롬프트를 모두 처리한 뒤 레퍼를 지우고 02번 원본으로 넘어갈게요.”

환경 제약은 현재 진행을 바꾸는 경우에만 한 문장 덧붙인다. 순차 교체를 안내할 때는 “현재 알파 버전으로, 이 배포본의 실제 사이트 자동 교체 검증은 아직 남아 있어요”처럼 실제 상태를 알린다. 환경 점검표 전체를 첫 답변에 출력하지 않는다. 이후에는 준비 결과와 사용자에게 필요한 행동을 안내한다.

## 1. 환경을 먼저 확인한다

### 흔한 첫 요청별 진행

| 사용자의 말 | 에이전트가 할 일 | 사용자에게 남길 행동 |
|---|---|---|
| “처음인데 어떻게 해?” | 접근 가능한 스킬·자료와 실행 능력을 확인하고 원하는 결과만 질문 | 작업 설명과 자료 전달 |
| “이 캐릭터 옷 바꿔줘” | 같은 원본 변형으로 구성. 변경 개수가 없으면 필요한 개수만 질문. 시트 구도는 자동 강제하지 않음 | 원본 업로드와 완성 JS 실행 |
| “사진 없이 이런 배경 만들어줘” | 텍스트 전용으로 구성, 레퍼 폴더를 요구하지 않음 | 사이트 기존 첨부 비우고 실행 |
| “이 폴더로 알아서 해줘” | 이미지·기획서에서 목적을 파악. 목적이 전혀 없으면 원하는 결과를 질문. 파일 수를 컷 수로 간주하지 않음 | 필요한 경우 목적 설명 |
| “캐릭터랑 이 배경 합쳐줘” | 복수 레퍼 지원 상태부터 확인. 현재 엔진의 미지원 사실을 알리고 자료·컷 기획까지만 준비 가능함을 설명 | 지원 전 실행을 요구하지 않음 |
| “아까 거 2번만 바꿔줘” | 기존 컷 목록과 진행 기록을 읽고 수정 범위를 반영. 접수된 요청을 전체 재실행하지 않음 | 새 파일의 적용 범위 확인 후 실행 |
| “안 돼” | 확보한 로그·화면부터 확인. 없으면 오류 문구 또는 입력창·패널 화면과 직전 행동 요청 | 코드 수정 대신 현상 전달 |

### 사용자에게 보여줄 파일

배포 폴더의 입구는 `처음_시작하기.txt`, 에이전트의 입구는 `SKILL.md`다. assets·scripts·references는 에이전트가 사용한다. 사용자가 이 폴더들을 직접 편집하거나 설치 위치를 알아야만 시작할 수 있도록 만들지 않는다.

작업 폴더에서는 원본 자료, 실제 연결할 레퍼 위치, 사용할 최신 실행 JS를 명확히 구분한다. 다른 ‘수정본·최종본·최종2’ 파일을 계속 늘리지 않는다. 필요하면 이전 실행본을 별도 보관하고 같은 전달 경로의 완성본을 갱신한다. 사용자 변경은 보존하고 파일 이동·이름 변경 시 연결을 함께 갱신한다.

첫 사용 안내는 짧게, 환경 차이 설명은 문제가 발생한 지점에서 제공한다. 처음부터 설치 설명·진단 표·구현 설명을 모두 나열하지 않는다. 결과가 나왔으면 결과를 확인할 위치와 후속 수정 요청 방법을 안내한다.

읽기 가능한 자료와 도구에서 확인하고, 꼭 필요한 미확인 항목만 한 번에 질문한다.

| 확인할 것 | 진행 기준 |
|---|---|
| 스킬 파일 | SKILL.md뿐 아니라 assets·scripts·references를 포함한 폴더 전체인지 확인한다. 엔진 버전을 읽는다. |
| 실제 작업 폴더 | 절대 경로와 실제 파일 목록을 확인한다. 다른 PC·클라우드 환경에서는 사용자의 로컬 경로에 접근된다고 가정하지 않는다. |
| 자료 해석 | 이미지·기획서를 읽을 수 있는지 확인한다. 파일 이름만 보고 인물이나 컷 역할을 확정하지 않는다. |
| 실행 파일 제작 | Python 3.10 이상으로 빌드 가능한지 확인한다. Node가 있으면 문법·회귀 검사에 사용한다. 없으면 미실시 검사를 명시한다. |
| 실제 사이트 | 연결된 브라우저의 Higgsfield 이미지 탭을 확인한다. 연결이 없으면 코드 준비는 가능하지만 실제 동작 검증은 할 수 없다. |
| 사이트 준비 | 로그인, 모델, Unlimited 사용 가능 여부, 현재 첨부 상태를 확인한다. 구독·크레딧·모델을 임의 변경하지 않는다. |
| 브라우저 환경 | 브라우저 이름·언어·화면 상태를 확인한다. 사이트 개편, 메뉴 위치, 업로드 방식 차이를 고려한다. 다른 브라우저·OS의 호환성을 미리 보장하지 않는다. |

에이전트 환경별 처리:

- 파일과 코드 실행이 가능하면 자료 확인·빌드·로컬 검사를 진행한다. 브라우저가 없어도 여기까지는 진행한다.
- 첨부만 읽을 수 있으면 작업 목록·프롬프트를 준비하되 사용자의 로컬 폴더를 수정했다고 말하지 않는다. 실행 파일을 만들 수 없다면 가능한 단계와 필요한 실행 환경을 명시한다.
- 브라우저가 연결되어도 콘솔 코드 실행·파일 업로드 도구가 없을 수 있다. 그때는 사용자가 해야 할 최소 단계만 안내하고 결과를 관찰한다.
- 필요한 자료가 없으면 추정한 프로젝트를 만들지 않는다. 독립적으로 진행할 수 있는 부분을 완료하고 누락 자료만 요청한다.

자료를 읽기 전 진행 알림 예시:

> 자료와 스킬을 읽고 어떤 방식으로 진행하면 좋을지 짧게 안내하겠습니다.

도구 확인 전부터 환경을 확정해서 위 문장을 그대로 복사하지 않는다. 환경 설명은 실제 확인된 내용으로 바꾼다.

## 2. 준비 결과를 짧게 보여준다

자료 수와 컷 수를 구분하고 컷마다 레퍼 역할·변형 수를 구성한다. 사용자가 지정한 개수를 쓰며 6개를 기본값으로 고정하지 않는다. 기획서의 장면과 기술 검증용 장면은 구분한다. 불명확한 매칭만 질문하고 매 단계 승인을 요구하지 않는다.

응답 예시:

> 이미지별 프롬프트를 준비했습니다.
> - 01번 이미지: 의상 변형 2개
> - 02번 이미지: 조명 변형 3개
> 01번의 두 요청을 처리한 뒤 레퍼를 지우고 02번을 올려 세 요청을 처리합니다.
> 원본은 보존했고 작업 위치는 `[실제 경로]`입니다.

개수는 요청한 값으로 바꾼다. 기본 순차 작업은 레퍼 한 장씩 사용한다. 합성이나 복수 레퍼 매칭은 별도 요청이 없으면 제안·요구하지 않는다. 시트 요청일 때만 얼굴 클로즈업·정면·후면 기본안을 적용한다.

## 3. 전달 파일과 시작 방법

실행 가능한 단계까지 완료된 경우 다음 내용을 짧게 전달한다.

> 실행 파일: `[최신 JS 링크]` · 버전 `[실제 버전]`
> `[레퍼 폴더]`를 사용합니다.
> Higgsfield 이미지 페이지 → F12의 Console → JS 전체 붙여넣기 → Enter → 폴더 연결 → 시작.
> 확인: `[실제로 통과한 검사]`. 미확인: `[남은 실제 동작]`.

레퍼 없는 작업은 폴더 연결 단계를 생략하고, 수동 레퍼 모드는 원본 업로드로 바꾼다. 붙여넣기 차단 경고가 있을 때만 `allow pasting` 직접 입력을 안내한다. JSON은 콘솔 실행 파일이 아니라고 설명한다. 탭을 유지하고 컴퓨터 절전을 끄도록 안내한다. 모든 화면 절전 방식·백그라운드 실행을 검증했다고 말하지 않는다.

새로고침하면 진행 기록이 유지되는지 구현을 확인한다. 현재 버전은 재가져오기를 지원하지 않으므로 새 코드에서 이미 접수된 항목을 제외해야 한다. 같은 세션의 이어서 실행과 페이지 새로고침 후 재실행을 구분한다.

## 4. 오류 응답 틀

**확인된 현상 → 아직 모르는 원인 → 다음 확인/조치 → 재개 위치** 순서로 답한다. 사용자를 탓하거나 모의 테스트 통과를 근거로 사이트가 정상이라고 단정하지 않는다.

업로드 예시:

> 업로드 입력칸을 0개 찾은 상태입니다. 메뉴를 열어야 하는지, 입력칸 위치가 다른지는 아직 확인되지 않았습니다. 현재 첨부 화면과 실행 파일 버전을 대조하겠습니다. 기존 레퍼를 먼저 지우지 말아 주세요.

접수 미확인 예시:

> 01번 컷의 3번 요청은 접수 표시를 확인하지 못했습니다. 성공으로 집계하거나 자동 재전송하지 않고 기록했습니다. 사이트 이력에서 이 요청을 확인해 주세요.

진단에 필요한 최소 정보:

- 브라우저·OS·사이트 언어, 사용 모델, 실행 파일/패널 버전
- 현재 컷·프롬프트 위치와 마지막 동작, 오류 문구
- 가능하면 입력 영역과 패널이 보이는 화면, 실제 실행한 JS

이미 확보한 정보는 다시 요청하지 않는다. 쿠키·토큰·계정 비밀번호·전체 콘솔/네트워크 덤프를 요구하지 않는다. 진단 파일에 프로젝트 프롬프트·파일명이 포함되면 공유 전에 확인하도록 설명한다. 서비스의 429/CSP 로그가 보인다는 이유만으로 자동화 실패 원인이라고 확정하지 않는다.

## 5. 검증 결과와 배포 안내

검증은 단계별로 적는다: 파일·문법 확인 / 모의 실행 / 실제 업로드·컷 전환·접수 / 결과 이미지 완성 확인. 한 단계의 통과가 다음 단계를 보장하지 않는다.

실제 검증을 하면 날짜, 브라우저·OS·사이트 언어, 모델, 엔진 버전, 레퍼 수, 실행한 컷·프롬프트, 관찰 결과를 기록한다. 미관찰 항목은 미검증으로 남긴다. 특정 환경에서 통과했다고 모든 환경 호환으로 표시하지 않는다.

최종 응답 예시:

> `[실제 경로]`의 최신 실행 파일을 갱신했습니다.
> 확인: 01번 원본의 프롬프트 묶음 처리, 기존 레퍼 삭제·02번 원본 업로드, 중단·재개 시 접수 확인된 항목 중복 없음.
> 이미지 완성 품질과 다른 브라우저 환경은 아직 검증하지 않았습니다.

이 예시는 해당 검증을 실제 수행한 경우에만 사용한다. 알파 배포에는 검증 환경·현재 제한·오류 제보에 필요한 최소 정보를 함께 제공한다. 추가 설치나 복잡한 설정을 첫 사용의 기본 조건으로 만들지 않는다.
